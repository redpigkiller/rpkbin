# 保證與假設

編譯成功表示產出的指令序列通過靜態驗證。要驗證目標描述是否符合模擬器，使用 `check-forms`。要驗證一個程式的機器碼是否重現 Python 的結果，使用 `verify` 或 `run_differential`。整合到既有程式之前，還要確認實際放置位址、外部函式、資料保留區和堆疊預算。

## 每次編譯的靜態驗證

驗證以編譯後的中間表示（IR）、最終的機器指令序列、Target 及呼叫介面為依據。它會獨立檢查配置器選出的結果。編譯器自身不變量的檢查失敗會得到 `InternalError`，含函式名稱及錯誤位置或原因。使用者的 encoder 回傳長度不符合 form 宣告時，得到含 form id 及期望、實際長度的 `TargetError`。

| 檢查 | 通過代表什麼 |
|---|---|
| V1 運算元與指令形式 | 最終指令的暫存器類別、立即值、位址及已解析的分支距離，符合所選形式的限制。 |
| V2 位元組數 | 每條指令的大小符合宣告，函式大小是各指令大小之和。若形式提供編碼器，也會檢查編碼結果的長度。 |
| V3 堆疊紀律 | 每條控制流路徑的 `push`／`pop` 深度從零開始、途中不為負，匯合處深度相同，每個回傳點的深度為零。有堆疊暫存的函式另外檢查 `park_depth`。 |
| V4 分支與旗標 | IR 的每個分支與跳躍在機器指令中有對應控制流。條件分支讀到的是配對的比較或與其語意相符的指令所設定的旗標。 |
| V5 呼叫介面與位置 | 每個呼叫攜帶的 ABI 與獨立取得的被呼叫者介面逐欄一致。同時要用且可能不同的值不會占用彼此重疊的位置。符合複製例外時可以共用。需要跨越呼叫保留的值已保存，並在回傳值搬移後還原。 |
| V6 指令來源與值流 | 可達的機器效果必須對應 IR 或合法的編譯器搬移、保存等動作。每個來源寫入、呼叫或 `asm` 恰有一次可達的對應效果，且保存、引數、回傳值、還原的順序正確。區塊內以符號值追蹤搬移、運算、讀寫與堆疊保存，檢查每個使用點拿到預期的值。 |
| V7 函式入口與出口 | 參數從 ABI 位置進入。每個可達的出口都回傳，控制流不會落出函式末端，跳躍或回傳後也不會在同一區塊留下無法執行的指令。回傳指令實際執行時值已到指定位置，應保留的暫存器與進入時相同，且回傳形式本身不會再破壞它們。 |
| V8 私有槽 | 槽位落在 spill pool 內，互不重疊且避開 ABI 固定位址。使用私有槽模式時，對 pool 內固定位置的機器存取限於編譯器產生的槽讀寫。 |
| V9 暫存器改動報告 | 依最終指令與被呼叫者介面重算的暫存器改動，與 `clobbers` 報告一致。 |
| V10 限制式比較旗標 | 使用 `borrow_msb0` 或 `nborrow_msb0` 實作比較前，驗證器會從最終 IR 獨立確認兩個運算元在該指令位寬下最高位元皆為 0。 |
| V11 堆疊暫存的值 | 每個暫存有正確配對的還原，區間巢狀或互不重疊。被保存的暫存器單位恰好等於被暫存的值所占單位，區間內無人使用該值，還原時也不覆寫仍會用到的值。驗證器確認推入的是預期的值，沿各條路徑追蹤堆疊上的值身分，核對分支匯合及迴圈回邊。 |

`verified: true` 表示靜態驗證在其涵蓋範圍內完成。`"partial: ..."` 表示靜態驗證通過且有使用抽象值追蹤的部分，原因附在字串中。例如呼叫內部行為、間接存取的實際位址與結果、別名部分的內容，都不能只靠區塊內符號追蹤得到完整證明。`"unverified: asm"` 表示此函式包含不透明的內嵌組語。靜態驗證仍檢查相關宣告、運算元配置和可檢查的效果，組語文字的實際行為由使用者負責。

靜態驗證依賴 Target 對指令形式、旗標、副作用與大小的宣告，也依賴 `@extern` 的 ABI 宣告。實際編碼、實際指令語意、所有可能輸入的行為，以及輸出文字在目的組譯器的放置結果，都需要個別驗證。若目標只在特定模式位元狀態下符合宣告，請在整合端維持該狀態，並由 `SimBinding.init` 為模擬測試設定相同狀態。

## 用模擬器檢查目標與程式

`check-forms` 以邊界及固定種子的取樣，比對指令形式的編碼與模擬器。檢查包括編碼長度、運算結果、旗標、記憶體、分支、堆疊及呼叫效果。結果依賴 `SIM` 是否正確描述目標，且取樣之外的值仍有可能出錯。目標作者可參閱 [指令形式與一致性檢查](target.md)。

`verify` 與 `run_differential` 會依函式及其依賴編譯與組譯測試程式，依固定種子取邊界值與隨機輸入，在全新模擬器內執行。外部函式需要對應的機器碼樁（stub）。每組輸入用同一初始資料執行 Python 參考語意，與模擬器比對回傳值、受檢資料記憶體，以及報告 `clobbers` 以外的基本暫存器。模擬器必須在步數上限內正常停機。參考執行的逾時會另計並略過該輸入，逾時比例超過 10% 時算失敗。含不透明 `asm` 的函式及需要它的測項會標為 `unverified: asm`。缺少所需形式而無法編譯的函式也會另列。

差異測試以實際執行的輸入為限。旗標、堆疊內容和堆疊指標不在預設比較項目中。Python 呼叫者可傳 `post_check(phase, sim)`，在 `"before"` 與 `"after"` 讀取模擬器狀態，例如確認堆疊指標相等。若檢查以 `AssertionError` 回報失敗，差異測試會把它記到該組輸入的結果。

### `window` 決定取樣範圍

`verify` 必須給 `--window`，Python API 則須給 `window`。下列兩種表示法擇一。`data` 是範例中的 Target 資料空間名稱。

| 表示法 | 行為 |
|---|---|
| `window=256` 或 `--window 256` | 各資料空間從位址 0 開始，隨機初始化 `[0, 256)` 中存在的 cell，另初始化 spill pool。整數只界定初始化範圍，參考執行實際觸及的其他 cell 也會比對。這是沿用的整數視窗模式，指標引數從 `0x80` 到 `0xFF` 避開 pool 取樣。 |
| `window={"data": (0x300, 0x5FF)}` 或 `--window data:0x300-0x5FF` | 為列出的資料空間指定含首尾的區間。每個區間須在空間位寬內，且至少 512 cells。CLI 可重複指定不同空間，位址可用十進位或 `0x` 十六進位。 |

使用第二種表示法時，從指標所屬窗口的下半部取樣。例如上表的指標引數從 `[0x300, 0x480)` 取樣，並包含 `0x300` 和 `0x33F` 的邊界樣本。這個範圍必須避開 spill pool，且每個指標引數的空間都要有窗口。有指定窗口的空間若出現窗口外的來源存取，該輸入會失敗。未列出窗口的空間可用常數位址存取，以零值為初始資料，該空間不納入記憶體結果比對。請選擇能涵蓋指標從取樣值加上程式自己的位移後可能讀寫的位置。

兩種模式都將 spill pool 排除於最終記憶體比對。差異測試會在參考執行中攔截來源程式落入 pool 的直接或間接存取，即使函式在保守模式下編譯也一樣。獨立呼叫 `run_reference` 沒有 pool 資訊，沒有這項檢查。詳細 API 與輸出解讀見 [使用指南](../README.md)。

## spill pool 是專用記憶體

`spill_pool` 指定由編譯器專用的一段資料記憶體，例如 `{"data": (0x600, 0x61F)}` 含兩端。空字典表示沒有可用的槽。請保留此範圍給同一編譯單元的暫存溢出和保存用途。每個函式分配到自己的槽，不與別的函式共用。同一份既有程式若整合多次獨立編譯的結果，仍須確保彼此的槽及其他使用者不會衝突。

選範圍時須避開來源的所有資料位址，包含直接常數、所有可能經 `Ptr` 指到的位置、外部函式的副作用及 ABI 中的固定記憶體位置。編譯器會先檢查區間是否在合法資料空間、是否超界或與 ABI 位置重疊。任意執行期指標、外部程式及其他呼叫環境的實際資料使用，要由整合者確認。違反私有槽契約時，行為未定義。

編譯器先用保守的別名規則配置，遇到 `AllocationError` 時，再以私有槽模式重試。在這個模式，編譯器可假定來源的間接存取不會動到 pool，並會以 `ConfigError` 拒絕檢出的來源常數位址與 pool 重疊。採用該模式的函式在報告有 `"pool_contract": "private"`。保留區的契約適用於每種模式。

## 堆疊暫存預算與選擇策略

`park_depth=0`（預設）停用堆疊暫存。原本用於函式保存、呼叫保存等用途的 `push`／`pop` 仍可出現在輸出。正值允許在值暫時用不到、稍後還要使用的區間內成對存入和還原。區間可以位於一個基本區塊內，也可以涵蓋入口及出口符合條件的自然迴圈。目標需提供能保存該值完整暫存器單位的 `push` 與 `pop` 形式。作為別名一部分的窄值，不能單靠會覆寫整個別名的還原形式來暫存。

`park_depth` 的單位是同時占用的 `push` 個數。`push_depth` 由本函式的最大深度及每個呼叫點的「當下深度 + 模組內被呼叫者的最大深度」取最大值。它包含 `preserves`、呼叫保存與堆疊暫存的用量。例：某呼叫點有兩筆尚未還原的保存，而被呼叫者最多另有三筆同時在堆疊上，該呼叫點計入五筆。只有輸出使用堆疊暫存的函式才受 `park_depth` 的限制。正深度的報告也列出 `parks`（採用的暫存區間數）與 `push_depth`，供整合時核對。

設定預算時，須先用目標的方式計算可用堆疊，扣除返回位址、既有呼叫環境的用量及外部函式的額外用量。外部函式在編譯器的深度公式視為 0。若外部環境有額外非同步堆疊用量，也須另行預留。實際的 8 位元與 16 位元保存可能占用不同位元組數，請把報告的 `push` 筆數依目標儲存方式換算。這套模型假定 `call`／`ret` 與 `push`／`pop` 共用一個後進先出的堆疊，被呼叫者返回時堆疊平衡。編譯器的使用範圍為無中斷、無重入、無遞迴的函式。

| `park_policy` | `park_depth > 0` 時的行為 |
|---|---|
| `smallest`（預設） | 在函式當下的編譯環境中，比較一般配置與堆疊暫存配置的成功結果。取位元組數較少者，平手保留一般配置。兩者皆失敗時回報一般配置的錯誤。 |
| `stack_first` | 一般配置若把值放進 spill 槽，且堆疊暫存配置成功，就採用堆疊暫存配置，即使輸出較大。 |
| `slot_first` | 只嘗試一般配置，機器碼與 `park_depth=0` 相同。報告仍有 `parks` 和 `push_depth`。 |

`smallest` 的大小比較以同一個函式、同一時間可用的槽及被呼叫者的 `clobbers` 為準。較早選用堆疊暫存的函式可能改變後續函式看到的配置條件，因此整份輸出和後續函式的大小仍可能增加。`park_depth=0` 時三種策略的輸出與報告相同。策略設定套用到整次編譯。

## 目標與最佳化的界線

- 語言只涵蓋 8 和 16 位元的無號資料及 8 位元記憶體 cell。需要的 16 位元算術或比較若缺少相應指令形式，編譯器不會通用地拆成 8 位元運算。基礎暫存器以 cell 為單位，可用別名描述較寬位置。
- 呼叫使用絕對目的位址。把組語貼到既有專案時，由整合者確認函式落在該欄位可達的位址範圍中，並確認標籤、指令模板與註解符合目的組譯器。`assemble` 用於依 Target 編碼與驗證，實際專案使用自己的組譯工具。
- 指令形式不涵蓋索引定址、融合的比較分支、專用位元指令與記憶體對記憶體搬移。旗標由比較與分支協作使用，無法當成可保存或傳遞的 `bool` 或進位值。也沒有間接呼叫、指令延遲槽、述詞執行或 SIMD 的模型。
- 以靜態位元組數為成本，使用確定性的啟發式。它可能找不到更短的等價指令序列，也無法保證全域最小值或執行速度。沒有精確求解器、指令排程、融合、迴圈反轉或展開、迴圈不變式外提、函式行內展開或程序抽取。
- 一般配置為每個值選定一個位置。區域性的成對保存、入口及出口搬移和堆疊暫存是支援的機制。沒有通用的存活區間切割、單一指令周圍的臨時溢出、重新物化常數或複製、專門保留的工作暫存器、配置回溯、跨函式槽覆疊，或將兩個窄值合併成單次寬保存。暫存區間內無法從堆疊讀回該值供中途使用，也不支援任意分支區域的暫存。
- 原始語言的其他限制見 [語言參考](language.md)。沒有 C 前端、GUI、語言伺服器或增量編譯。
